# Schema Code Cache - Usage Guide

## Overview

The schema code cache dramatically accelerates code generation by caching previously generated extractors indexed by schema signature.

### Performance Impact

```
Cache HIT (same schema as before):
  Time: 0.01s (virtually instant)
  Speedup: 841x faster than vLLM

Cache MISS (new schema):
  Time: 4.6s (calls vLLM, then caches)
  
Real-world at scale:
  1,000 documents with only 5 unique schemas:
  - Without cache: 1,000 × 4.6s = 4,600s (1.28 hours)
  - With cache:    5 × 4.6s + 995 × 0.01s = 33s (98% faster!)
```

## How It Works

**Schema Hashing:**
```
Input:  columns = [
          {name: "ID", type: "integer"},
          {name: "Name", type: "string", pii: "PERSON_FULL_NAME"}
        ]

Hash:   SHA256([column_name, type, pii_field for each column])
Result: "abc123def456"  (first 16 chars)

Same schema → Same hash → Same cached code
```

**Cache Lookup:**
```
1. Compute hash from schema
2. Query SQLite: SELECT code WHERE schema_hash = hash
3. If found: Return immediately (0.01s)
4. If not found: Call vLLM (4.6s), cache result
```


## Using the Cache

### Basic Usage (Automatic in Tool 3)

```python
from tools import get_tool_by_name

tool3 = get_tool_by_name("generate_parser_script")

# First call: cache miss, calls vLLM
response = tool3({
    "guid": "doc-001",
    "columns": columns,
    "detected_schema": schema,
    "raw_sample": sample,
})

result = json.loads(response)
print(f"Cache hit: {result['cache_hit']}")           # False
print(f"Generated by: {result['code_quality']['generated_by']}")  # vLLM
print(f"Time: {result['generation_time_sec']}s")      # 4.6s

# Second call (same schema): cache hit, instant
response2 = tool3({
    "guid": "doc-002",
    "columns": columns,  # SAME columns
    "detected_schema": schema,
    "raw_sample": different_sample,
})

result2 = json.loads(response2)
print(f"Cache hit: {result2['cache_hit']}")          # True
print(f"Generated by: {result2['code_quality']['generated_by']}")  # cache
print(f"Time: {result2['generation_time_sec']}s")     # 0.0s
```

### Advanced Usage (Direct Cache Access)

```python
from extraction.schema_code_cache import get_cache

cache = get_cache()

# Get cached code (returns None if not cached)
code = cache.get(columns)

# Manually add to cache
cache.set(columns, generated_code)

# View statistics
stats = cache.get_stats()
print(stats)
# {
#   'total_schemas': 127,
#   'total_hits': 5432,

#   'max_hits_per_schema': 1240,
#   'cache_size_mb': 2.6,

# Print formatted stats
cache.print_stats()

# Clear cache (for testing)
cache.clear()

# Cleanup if over limit
cache.cleanup_if_needed()  # Removes bottom 10% least-used
```

## Cache Invalidation

The cache uses **structural hashing** - it automatically invalidates when:

❌ Column name changes
❌ Column type changes (e.g., string → integer)
❌ PII mapping changes (e.g., PERSON_FULL_NAME added)
❌ Column order changes

The cache does **NOT** invalidate when:
✅ Sample data changes (only affects extraction examples)
✅ Document GUID changes
✅ Extraction results change

## Cache Management

### Automatic Cleanup

Cache automatically removes least-used entries if it exceeds `max_schemas` (default: 10,000):

```python
# In schema_code_cache.py
max_schemas = 10000  # If exceeded, remove bottom 10% least-used

# Triggers on each cache.set() call
cache.cleanup_if_needed()
```

### Manual Maintenance

```python
cache = get_cache()

# Remove specific schema
db = sqlite3.connect("cache/schema_code_cache.db")
db.execute("DELETE FROM code_cache WHERE schema_hash = ?", (hash,))
db.commit()

# Clear entire cache
cache.clear()

# Reorganize database (optimize space)
db.execute("VACUUM")
```

## Database Details

### Schema

```sql
CREATE TABLE code_cache (
    schema_hash TEXT PRIMARY KEY,           -- SHA256 of schema
    schema_json TEXT NOT NULL,              -- Full column definitions
    code TEXT NOT NULL,                     -- Generated extraction code
    code_length INTEGER,                    -- Code size in bytes
    created_at DATETIME DEFAULT NOW,        -- When first cached
    last_hit_at DATETIME,                   -- Last cache hit time
    hit_count INTEGER DEFAULT 0             -- Number of cache hits
);

CREATE INDEX idx_hit_count ON code_cache(hit_count DESC);      -- For cleanup
CREATE INDEX idx_created_at ON code_cache(created_at DESC);    -- For analytics
```

### SQLite Properties

- **Mode**: WAL (Write-Ahead Logging) for concurrent access
- **Locking**: Automatic reader/writer locking for 96+ workers
- **Isolation**: Serializable (default)
- **File**: ~35 bytes per entry overhead + code size

## Troubleshooting

### Cache not hitting

**Problem**: Cache hit rate is 0%

**Check**: Are you changing the schema between calls?

```python
# Bad: Different schema each call
columns1 = [{"name": "ID", "type": "int"}]
columns2 = [{"name": "ID", "type": "integer"}]  # Different type string!

# Good: Consistent schema
columns = [{"name": "ID", "type": "integer"}]
```

### Cache growing too large

**Problem**: `schema_code_cache.db` is > 100MB

**Solution**:
```python
cache = get_cache()
cache.cleanup_if_needed()  # Removes bottom 10%
cache.print_stats()         # See what was removed
```

### Stale cache after code update

**Problem**: Updated the prompt but cache still has old code

**Solution**:
```python
cache = get_cache()
cache.clear()  # Full reset
```

## Integration with 96-Worker Pipeline

The cache is **thread-safe** for concurrent access:

```python
# workers.py
for worker in range(96):
    # Each worker uses the same cache safely
    cache = get_cache()
    code = cache.get(columns)  # Safe concurrent reads
    cache.set(columns, code)   # SQLite handles write queueing
```

No locking code needed - SQLite handles it automatically!
